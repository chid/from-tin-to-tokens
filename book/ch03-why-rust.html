Part I: Foundations

Why Rust

The stakes at this layer

Building an inference compute stack means writing raw ioctl structures that match kernel headers, managing device memory addresses, and constructing binary command packets byte by byte, all without a garbage collector, a runtime, or any abstraction between you and the driver.

It also means doing that without C’s usual accompaniments, the use-after-frees and buffer overflows and dangling pointers. On a datacentre GPU those don’t politely segfault your process. Depending on how fault handling is configured, a bad device pointer can wedge the command processor, trigger a device reset, and take down every workload on the machine, so the cost of a memory safety bug at this layer isn’t a stack trace, it’s an incident.

Rust gives you C-level control without C’s usual accompaniments. But the argument for Rust here isn’t the generic memory-safety pitch, it’s something more specific, and it took building one of these to see it clearly.

The unsafe boundary is the architecture

The natural shape for a Rust inference stack is a boundary between two crates.

platform-sys    — raw, unsafe, hand-encoded kernel ioctls
platform-core   — safe device APIs, GPU dispatch, attention kernels

The sys crate is deliberately unsafe. It holds repr(C) structs mirroring kernel headers, libc::ioctl calls, and raw file descriptor operations, and every function is unsafe fn because the caller has to guarantee the fd is valid and the arguments are correct. That crate is auditable in a way generated bindings aren’t, since you can put it beside the kernel header and check it field by field.

The core crate wraps all of that in a safe API. open() hands back a struct owning the device fd through OwnedFd , alloc_vram() returns a DeviceBuffer that owns its allocation handle and frees it on Drop , and dispatch() takes a typed Kernel , a KernargBuilder , and grid dimensions. A caller using the safe API can’t hand a raw host pointer to a GPU kernel argument without writing unsafe , because the safe API never exposes raw pointers in the first place.

That boundary is the architecture. It isn’t a style preference, it’s the load-bearing design decision, and misusing a device pointer above the boundary becomes a compile error rather than a hardware fault.

It’s worth being precise about what the boundary buys and what it doesn’t, because overselling it is how people get surprised later. The type system gives you spatial safety, meaning no double-free, no useafter-free of the Rust object, no confusing a device virtual address with a host pointer. It can’t give you temporal safety against the device, because the GPU runs asynchronously and dropping a DeviceBuffer the command processor is still reading is a use-after-free that no borrow checker can see. The borrow is held by hardware. Enforcing that stays manual, through kernarg slot management and wait-before-drop discipline in the dispatch loop, and Chapters 7 and 25 cover the machinery.

Two more limits worth stating plainly. repr(C) guarantees Rust lays a struct out the way C would, but nothing verifies your struct matches this kernel’s header, so that check is either a human reading two files or a test asserting size_of and offset_of against known constants. And the compiler can’t see inside the GPU kernel at all, so whatever the code object does with the arguments you hand it sits entirely outside Rust’s guarantees.

Why the dispatch loop isn’t async

Write packet, ring doorbell, poll signal. That loop is synchronous, and it wants to stay that way.

It’s a busy-poll on a memory-mapped value, not an I/O operation, so adding tokio or any async runtime would bolt a reactor and a thread pool onto something already measured in microseconds, introduce wakeup latency of the same order as the operation itself, and solve a multiplexing problem the compute path doesn’t have. The loop is deliberately fn rather than async fn , and when the compute path needs concurrency, as it does for multi-GPU collectives, it uses threads pinned to devices.

None of which means async has no place. The serving layer above, with its HTTP handling and request queuing and streaming responses and cancellation, is naturally async and tokio with axum is exactly right for it. The separation mirrors the architecture, sync for compute and async for serving, with an explicit boundary between them, usually a channel and a dedicated executor thread. Getting that boundary wrong, by running model steps on the async runtime’s worker pool, is one of the most common performance bugs in Rust serving code, because a 30 ms blocking model step starves every other task sharing that worker.

What Rust costs you

The trade-offs are real and it would be dishonest to skip them.

Compile times are a genuine tax on iteration, tens of seconds for an incremental check and minutes for a clean release build, which is worth spending effort on through workspace splitting, cargo check in the inner loop, and a fast linker.

The GPU ecosystem is thin. There’s no mature Rust path for AMD kernel compilation, no first-class Rust CUDA driver binding, no Rust GPU profiler. Kernels get written in OpenCL C or HIP or CUDA C, compiled at build time, and loaded by parsers you write yourself.

FFI friction never fully goes away, since every kernel struct has to be mirrored exactly and the compiler can’t verify the mirror is faithful. And unsafe doesn’t disappear either. The sys crate is entirely unsafe and the core crate has unsafe blocks for pointer dereferences, volatile access, and mmap. The safety boundary is a discipline rather than a proof.

Why a from-scratch builder uses none of the Rust ML ecosystem

Candle, Burn, tch-rs, and mistral.rs all exist and all work, and a from-scratch stack that intends to sit below the vendor runtime uses none of them, for one architectural reason. Every one of those libraries sits on a vendor runtime, so pulling one in would reintroduce exactly the layer you set out to eliminate.

That’s not a criticism, they serve a different purpose. For building inference applications on existing runtimes they’re excellent, and writing your own driver bindings for that job would be malpractice.

What a from-scratch builder does use is the foundational crates. serde for model metadata, bytemuck for byte casting, libc for ioctls, memmap2 for checkpoint mapping, sha2 for integrity checks, rayon for host-side preprocessing. Everything GPU-specific, the ELF loader and ioctl bindings and packet constructor and kernarg builder and signal polling, gets built.

What C gives you, and what Rust gives you instead

C gives direct memory access, zero-overhead abstraction, and complete hardware control, along with use-after-free, buffer overflows, and undefined behaviour. C++ adds RAII and templates while keeping the footguns and throwing in a build system that turns cross-language integration into a project of its own.

Rust gives the same control, since unsafe blocks provide raw pointer arithmetic and volatile access and FFI, while wrapping the common case in a type system that eliminates the most dangerous bug classes and making the boundary explicit. You know exactly where the type system has stopped protecting you, and those are the blocks you audit.

For GPU work specifically, the sharpest advantage is the newtype pattern. In C a device pointer is a raw u64 , indistinguishable from a host pointer or a handle or a length. In Rust a DeviceBuffer wraps that u64 in a type that can’t be confused with anything else, can’t be constructed outside the allocator, and can’t be cloned by accident, which turns an entire class of runtime bugs into compile errors.

The second advantage gets discussed less and matters more over a project’s life, and that’s fearless refactoring . At this layer the design you want in month six isn’t the design you wrote in month one, and the difference between a stack that keeps improving and one that ossifies is whether you can restructure the memory model or the dispatch path without introducing silent corruption. When the compiler enumerates every break you rewrite, and when it doesn’t you work around, and working around is how systems calcify.

Key Concept

Rust’s value in an inference stack is the unsafe boundary, raw kernel interfaces in an unsafe crate with safe APIs above. The type system prevents spatial pointer mistakes at compile time, while temporal safety against an asynchronous device stays a manual discipline, as does verifying that repr(C) mirrors match the real headers. The dispatch loop is synchronous by design and async belongs to the serving layer behind an explicit boundary. The Rust ML ecosystem serves application-level inference on existing runtimes, so a from-scratch builder works below it rather than on top of it.

Exercises

  1. Write the safety contract for a function returning &mut [u8] that aliases GPU-visible memory. What must the caller guarantee, and what mechanism in the dispatch loop actually enforces it? Then explain why the receiver has to be &mut self rather than &self , and what goes wrong before the GPU is involved at all if it isn’t.

  2. Give a concrete example of a bug that repr(C) doesn’t prevent, then design a test that would catch it at build time.

  3. A colleague proposes running model steps as tokio tasks so the server can “handle more concurrency.” Explain in terms of the executor’s scheduling model why this reduces throughput, and describe the correct structure.
