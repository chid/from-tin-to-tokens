Part IX: Proof, Testing, and Production

Performance Measurement

The roofline in practice

Measure sustained bandwidth with a pure streaming kernel, which on MI355X gives about 5,800 GB/s against an 8 TB/s spec. Measure achievable compute with a large well-shaped GEMM at each precision you use. Compute the ridge point from your measured numbers, roughly 310 FLOP/byte for FP16 on MI355X using spec bandwidth and higher using sustained. Place your kernel using bytes actually moved from HBM. Then account for the gap with named mechanisms rather than adjectives.

That last step separates performance engineering from performance observation. “We’re at 59% of the ceiling” is a measurement. “We’re at 59%, of which 12 points are the combine tree’s serialisation and 20 are prefetch ramp-up in the first window” is a plan.

Getting the arithmetic right

achieved_bandwidth = (bytes_read + bytes_written) / kernel_time

The parentheses matter. Printed without them the expression computes something else entirely, and that typo is common enough to be worth guarding against. More substantively, be careful what you count.

Count bytes that actually cross the HBM interface, because data served from L2 or Infinity Cache inflates apparent bandwidth beyond the physical maximum, which is a useful signal in itself. Computing 12 TB/s on an 8 TB/s part means your working set is in cache. Count writes as well as reads. And for quantised data, count stored bytes rather than dequantised ones.

Per-kernel timing

Measure dispatch-to-completion per kernel and, separately, wall-clock per layer, because the difference is host overhead and it’s frequently the largest term in an unoptimised stack (Chapter 25).

For chained dispatches you can’t time individual kernels without breaking the chain, which changes what you’re measuring, so time the whole chain and keep a separate unchained build for per-kernel attribution.

Two GPU-specific traps. Clocks boost and throttle, so a benchmark run cold reports boost clocks the same kernel will never see in production, which means warming up until clocks are stable and recording them. And the first launch is different , with code object load, cold caches, a cold allocator, and on a runtime a JIT, so never include it.

End-to-end metrics

TTFT is arrival to first token, queueing plus prefill. TPOT or inter-token latency is the perceived streaming rate. Tokens per second per GPU is the cost-relevant throughput. And goodput is tokens per second delivered by requests that met their SLOs, which is the metric that should drive decisions (Chapter 16).

Always report distributions rather than means, because a system with a 20 ms mean TPOT and a 400 ms P99 feels broken to a meaningful fraction of users and its mean says nothing about that.

Benchmarking honestly

The failure modes, each of which shows up regularly in published comparisons.

Mismatched batch size , comparing your batch-1 latency against another system’s batch-64 throughput, which is the most common error and usually unintentional. Mismatched precision , since FP8 against FP16 isn’t a comparison of engines. Mismatched context , because decode speed depends strongly on context length, so state it. Mismatched output length , since short generations are dominated by prefill and startup. No warmup , or warmup included in the measurement. Cherry-picked runs , reporting the best rather than the median and the tail. Uncontrolled environment , where other tenants and other processes and thermal state and clock behaviour move results by more than most optimisations do. And ignoring correctness , because a fast wrong answer isn’t a data point, which is why every performance claim in this book is paired with a correctness result for the same configuration.

A useful discipline is to write down the full configuration, model and precision and context and batch and hardware and driver version and engine version and sampling parameters, before running, and publish it with the number. If the configuration is embarrassing to state, the number isn’t real.

Load generation

Constant-rate load generators produce results that don’t match production, because real arrivals are bursty and real requests have correlated lengths. Better practice offers three options.

Closed-loop , with N concurrent clients each sending the next request on completion, measures throughput at a given concurrency and is what most engine benchmarks use. Open-loop , with Poisson or trace-replay arrivals independent of completion, measures what happens under overload, which is what actually breaks systems and the only way to observe queueing collapse. And trace replay from production logs preserves prompt-length distribution, output-length distribution, and prefix-sharing structure, the last of which is invisible to synthetic generators and can change throughput by multiples.

Report the goodput curve , offered load on the x-axis and goodput on the y. Every real system’s curve rises, peaks, and then falls as overload sets in, where the peak is your capacity and the shape after it tells you whether the system degrades or collapses.

Profiling

Nsight Compute and Systems on NVIDIA give per-kernel counters, memory throughput, occupancy, warp stall reasons, and source attribution, and it’s the strongest tooling in this space. rocprofv3 and ROCm Systems Profiler , the tool formerly called Omnitrace, on AMD give kernel timing, hardware counters, and traces. perf and friends cover host overhead, time in ioctls and polling and packet construction and tokenisation and detokenisation and scheduling, and you should never assume the bottleneck is on the GPU, because in a serving system it frequently isn’t. A Python scheduler saturating one core while eight GPUs idle is a common failure and entirely invisible if you only profile kernels. And distributed tracing covers the request path end to end (Chapter 38).

Standard benchmarks

MLPerf Inference provides comparable, audited numbers across vendors with defined scenarios, singlestream and server with latency constraints and offline, plus accuracy requirements, and that accuracy requirement is what stops quantisation from becoming a free win. Its value is comparability and its limit is that its workloads may not resemble yours.

For engine-level comparison, each major engine ships a benchmark harness, and using theirs rather than writing your own removes a large class of accidental unfairness.

Key Concept

Measure sustained bandwidth and achievable compute on your own hardware, place kernels on that roofline using bytes actually moved, and explain every gap with a named mechanism. Report TTFT, TPOT, throughput, and goodput as distributions. Match batch size, precision, context, and output length before comparing anything, warm up, control the environment, and pair every performance claim with a correctness result. Use open-loop or trace-replay load to see how the system behaves past its capacity, because that’s what production does to it.

Exercises

  1. A kernel reads 302 MB and writes 8 KB in 346 µs. Compute achieved bandwidth and the fraction of a 5,800 GB/s ceiling. What single architectural property of the access pattern most plausibly explains the gap?

  2. Design an apples-to-apples comparison between two engines on the same hardware. List every parameter you have to fix and how you’d verify each.

  3. Sketch goodput-against-offered-load curves for a system with admission control and one without, and explain the difference past the peak.

  4. Build: implement an open-loop load generator with configurable arrival process and length distributions, and produce a goodput curve for your system at a stated SLO pair.
