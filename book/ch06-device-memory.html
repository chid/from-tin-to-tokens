Part II: The Hardware Layer

Device Memory

Memory types

Device-local VRAM is the fastest memory on the GPU and it’s where weights and KV cache belong, accessed through device virtual addresses.

Host memory mapped to the GPU , called GTT on AMD and pinned host memory on NVIDIA, lives in system RAM and gets mapped into the GPU’s address space. The GPU can reach it, but every access crosses PCIe, and on a PCIe 5.0 ×16 link that’s about 64 GB/s against 8 TB/s of HBM, a 125× gap . Legitimate uses are staging buffers, host-written control structures, and small metadata read once. Illegitimate use is anything a kernel touches in its inner loop.

Coherent or fine-grained memory stays coherent between CPU and GPU without explicit flushes. On AMD with large BAR, VRAM can be CPU-mapped and made coherent with the right allocation flags, and on NVIDIA managed memory provides similar semantics with driver-managed migration. Coherence isn’t free, since fine-grained allocations can bypass caches, so use it for synchronisation flags and signals rather than bulk data.

The large-BAR advantage

Modern datacentre GPUs support large BAR , which maps the entire VRAM into the host’s address space, and the implication is more architecturally significant than it first appears. One VRAM allocation has one virtual address that works from both CPU and GPU, so you can host-write a kernarg buffer straight into VRAM and have the GPU read it with no copy, or host-read a completion signal without a transfer.

Without large BAR only a small window, historically 256 MB, is host-visible and everything else needs explicit copies. Large BAR is what makes the “write the packet, ring the doorbell” model of Chapter 7 as simple as it looks.

There’s a catch worth knowing. Host-visible doesn’t mean fast to access from the host, because CPU reads of VRAM over PCIe are uncached and slow, so a host-side loop polling a VRAM location pays a PCIe round-trip per read. Poll signals in host memory or with appropriate caching hints, and keep bulk data in VRAM.

Peer mapping

In a multi-GPU system, peer mapping makes a buffer allocated on one GPU addressable from another. The data stays where it was allocated and the access becomes real GPU-to-GPU traffic over the fabric, Infinity Fabric on AMD and NVLink on NVIDIA.

The mechanism is three steps. GPU A allocates a buffer in its VRAM, that buffer gets mapped into GPU B’s virtual address space through MAP_MEMORY_TO_GPU with B’s gpu_id , and B’s kernels can then load and store to it. Every collective in Chapter 28 is built on exactly that, peer buffers plus remote writes plus synchronisation through signals or system-scope atomics.

The wrong-memory-space bug

The most insidious bug in low-level GPU programming doesn’t crash anything. A buffer sitting in host memory instead of device memory works perfectly, it’s just that every access quietly crosses PCIe, and the only symptom is that your kernel is inexplicably slow.

It’s easy to hit precisely because you control placement explicitly. A flag set wrong, an allocation helper that falls back to host memory when device allocation fails, a scratch buffer created by a different code path from the main ones, any of those pins a pipeline at a fraction of its speed.

The diagnostic signature is distinctive and worth committing to memory. A performance floor that doesn’t move when you change the kernel. If three structurally different implementations all land on the same number, the bottleneck isn’t in the code you keep rewriting. Chapter 4 describes the instance of this that cost a rewrite cycle, and the fix was a single allocation call.

Defences, in order of how well they work. Make device allocation the default and host allocation the explicitly named exception. Record the memory type in the buffer type so it’s visible at every call site. And add a debug mode that walks every buffer a kernel will touch and asserts its residency before dispatch.

Memory ownership in Rust

Rust’s ownership model maps onto GPU memory lifetime almost too neatly.

A device pointer is a raw u64 , which in C is indistinguishable from a host pointer or a handle or a length, so the newtype pattern earns its keep immediately.

pub struct DeviceBuffer {
    handle: u64,    // KFD allocation handle
    va: u64,        // device virtual address
    size: u64,
    kfd: Arc<Kfd>,  // keeps the device fd alive
}

impl DeviceBuffer {
    pub fn device_ptr(&self) -> u64 { self.va }
    pub fn len(&self) -> u64 { self.size }
}

DeviceBuffer can’t be constructed except through the allocator and its va isn’t reachable as a bare integer from outside the module, so a function taking &DeviceBuffer can’t be handed a host pointer by accident.

DeviceBuffer::drop unmaps and frees the allocation, which gives you RAII for VRAM and eliminates both the leak, the most common failure mode in a long-running server, and the double-free. And wrapping the KFD fd in OwnedFd inside an Arc<Kfd> turns “the fd must outlive every allocation and queue” from a convention into an ownership invariant.

What the type system can’t do

All of that gives you spatial safety and none of it gives you temporal safety, because the GPU runs asynchronously and a buffer may still be in use by the command processor when Drop executes.

If the GPU is mid-read when the memory gets freed and reused, you have a GPU-side use-after-free, and depending on fault configuration that ranges from silently wrong results to a VM fault that wedges the command processor and needs a device reset. During mainarch’s collectives work an unguarded device-side spin did exactly that, wedging the compute command processor badly enough that queues couldn’t be evicted and the GPU only recovered when the process exited.

The mitigation is discipline rather than types. Wait on the relevant completion signal before dropping any buffer the GPU might be using, and track in-flight work explicitly, which is what the kernarg slot counter of Chapter 7 is for. The type system is the first line of defence, the dispatch discipline is the second, and a watchdog is the third.

Safe views into GPU-accessible memory

For host-side fills before dispatch you need to write into GPU-visible memory, and the contract is temporal.

impl DeviceBuffer {
    /// # Safety
    /// The caller must ensure no GPU work that reads or writes this buffer
    /// is in flight. In practice: call after `wait()` on every dispatch that
    /// referenced it.
    pub unsafe fn as_mut_slice(&mut self) -> &mut [u8] {
        unsafe {
            core::slice::from_raw_parts_mut(self.va as *mut u8,
                                            self.size as usize)
        }
    }
}

Note the &mut self . Taking &self here compiles and is unsound: the returned lifetime is tied to a shared borrow, so two &mut [u8] over the same VRAM can exist at once and you have aliasing mutable references, which is undefined behaviour before the GPU is even involved. It is an easy thing to write in a hurry and it undoes the entire argument of Chapter 3, in the one function where that argument is load-bearing.

Which is the honest lesson about the safe boundary. It only holds if the signatures are right, and unsafe fn does not exempt you from getting the borrow right. Writing the contract down isn’t bureaucracy either. The unsafe blocks are the ones you audit, and one with a stated contract can be checked against its call sites while one without it can’t.

Key Concept

On the raw driver interface you own where every byte lives, and a buffer in the wrong memory space is a silent 125× performance bug rather than a crash. Rust’s ownership model maps cleanly onto GPU memory, with newtypes preventing pointer confusion, Drop giving RAII, and OwnedFd enforcing handle lifetime, but temporal safety against an asynchronous device stays manual. A performance floor that doesn’t move when you change the kernel is almost always a placement bug.

Exercises

  1. A kernel reads 512 MB from a buffer once per invocation. Compute its runtime with the buffer in VRAM at 5,800 GB/s and with it in host memory behind PCIe 5.0 ×16. What ratio do you expect, and why might the measured ratio be smaller than the bandwidth ratio?

  2. Design an API that makes the wrong-memory-space bug impossible to express rather than merely detectable. What does it cost in ergonomics?

  3. Build: allocate two buffers, one device-local and one host-mapped, and time an identical streaming kernel over each. Then deliberately place a few-KB scratch buffer in host memory inside an otherwise devicelocal pipeline and measure what happens.
