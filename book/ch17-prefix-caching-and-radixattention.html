Part IV: The Serving Engine

Prefix Caching and RadixAttention

The observation

Requests to a real inference server share prefixes constantly. Every request in a chat application starts with the same system prompt, few-shot prompts share their examples, multi-turn conversations resend the entire history each turn, agentic loops resend a growing transcript on every tool call, and RAG pipelines resend the same retrieved documents.

Without prefix caching, every one of those recomputes KV for tokens that were computed moments earlier by a nearly identical request.

This is frequently the largest single win available in a deployment, and it requires no kernel work whatsoever, which makes it an unusually good place to start.

Hash-based prefix caching

vLLM’s approach identifies each full KV block by a hash of its token IDs chained with the hash of the preceding block , so identical content at different positions hashes differently and the match is genuinely a prefix match rather than a coincidence. On arrival, hash the prompt block by block, look each one up, and on a hit map the cached physical block into the new sequence’s block table and bump its reference count, stopping at the first miss and computing the rest.

It’s simple, O(1) per block, and composes cleanly with the block allocator, which is why it’s on by default.

Its limitations come from block granularity. Matching happens in whole blocks, so a shared prefix ending mid-block leaves that block uncomputable from cache, and blocks whose content matches while their preceding context differs won’t match, which is correct behaviour rather than a bug.

On hash collisions, the theoretical risk of two different token sequences hashing identically is real and negligible with a 64-bit-or-wider hash. Engines that care store the token IDs and verify on hit, and since a collision would produce silently wrong output, that verification is cheap insurance.

RadixAttention

SGLang maintains a radix tree whose edges are token sequences and whose nodes hold references to KV storage.

root
├── [system prompt A] ────────► KV for A
│   ├── [user turn 1] ────────► KV for A+1
│   │   └── [assistant reply] ► KV for A+1+r
│   └── [user turn 2] ────────► KV for A+2
└── [system prompt B] ────────► KV for B

On arrival you traverse from the root matching tokens, the deepest match is the reusable prefix, and the remainder gets inserted as a new branch, splitting a node if the divergence falls inside an existing edge.

The properties that matter are longest-prefix match in time proportional to the matched length, node splitting so the tree adapts to whatever prefixes actually occur rather than to a fixed block grid, structureaware eviction where leaves go before internal nodes since an internal node is a prefix of everything beneath it, and automatic sharing, because two requests with a common prefix share it without anyone arranging that. Where the underlying KV pool is token-indexed the reuse granularity is a token, and where it’s page-indexed the practical granularity is a page, same as hashing.

SGLang’s evaluation reports up to about 6.4× higher throughput than prior systems on workloads with heavy prefix sharing, which is the honest form of the “5 to 10×” figure that gets quoted around. On workloads with no sharing the benefit is zero and the bookkeeping is a small loss.

Cache hit economics

A full hit skips prefill entirely and the request goes straight to decode, which for a 2,000-token system prompt on a large model removes tens of milliseconds from TTFT and frees the corresponding GPU time for someone else. A partial hit prefills only the uncached suffix, which is the common case in multi-turn chat where each turn’s cached prefix is the whole previous conversation. A miss is a full prefill.

The metric to instrument is the cached-token fraction , cached prefill tokens over total prompt tokens. It predicts TTFT and prefill GPU time better than any other single number, and it’s the first thing to look at when a deployment’s TTFT regresses.

Where prefix caching gets hard

Cache scope. With tensor parallelism every rank holds part of every block, so cache state has to agree across ranks, meaning decisions get made once and broadcast rather than made independently. With data parallelism across replicas, a request routed to a different replica misses a cache that exists elsewhere, which is why prefix-aware routing at the load balancer is worth as much as the cache itself.

Capacity. The prefix cache competes with running sequences for the same pool, so too much retention starves concurrency and too little destroys hit rate. That’s a tuning problem with a measurable objective, maximise hit rate times prefill saved minus preemptions caused, and it’s worth actually measuring.

Correctness of what gets shared. Two requests can share tokens without sharing everything that affects KV, because they might use different LoRA adapters, different positional scaling configurations, or different cache quantisation. The cache key has to cover every input that changes the computed KV, or you’ll serve one tenant’s adapter output to another, which makes this a security boundary rather than merely a correctness one.

Multi-tenant isolation. Shared prefix caches leak timing information, since a fast TTFT reveals that someone else recently sent the same prefix. For adversarial multi-tenancy you partition the cache per tenant and accept the hit rate loss.

Beyond one node

The natural extension is a KV cache tier below VRAM, host RAM or local NVMe or a cluster-wide store, so a prefix evicted from GPU memory can be restored rather than recomputed. The comparison is the same one as always. Restoring N tokens of KV costs bytes over link bandwidth, recomputing them costs

N over the prefill rate, and for long prefixes over a fast fabric restoring wins. That’s the foundation of the KV-centric architectures in Chapter 30.

Key Concept

Prefix caching exploits the fact that real workloads resend the same prompt prefixes constantly. Hashbased caching is simple and block-granular with chained hashes, RadixAttention uses a radix tree with node splitting, longest-prefix match, and structure-aware eviction, reported at up to 6.4× throughput on sharing-heavy workloads. The cache key has to cover everything that affects the computed KV, adapter and position scaling and quantisation included, or sharing becomes a correctness and security bug.

Exercises

  1. A chat workload has a 1,500-token system prompt and turns averaging 200 tokens, with 8 turns per conversation. Compute total prefill tokens with no caching, with block-granular caching at block size 16, and with ideal token-granular caching.

  2. Explain why block hashes must be chained with the previous block’s hash, and construct a concrete failure case for unchained hashes.

  3. Design the cache key for a system serving multiple LoRA adapters and two RoPE scaling configurations. What’s the security consequence of omitting either?

  4. Build: implement a radix tree over token sequences with reference counting and LRU eviction of leaves. Replay a synthetic multi-turn chat trace and report the cached-token fraction.
