Part V: Model Execution

Adapters and Multimodal Inputs

Two features turn a single-model runner into a platform, and both change the serving engine’s structure rather than only its kernels. Which is the interesting part, because if your abstractions are right they absorb both with modest work, and if they aren’t, each one is a rewrite.

LoRA and multi-adapter serving

Low-rank adaptation replaces a fine-tuned copy of a model with a small pair of matrices per adapted weight, W' = W + (B·A)·(α/r) , where A is r × in, B is out × r, and r is typically 8 to 64. For a 70B model an adapter is tens of megabytes rather than 140 GB.

The naive serving approach merges the adapter into the weights and loads a separate model per adapter, giving full speed and no sharing, and it doesn’t scale past a handful of adapters.

The interesting problem is serving many adapters concurrently against one base model, which the S- LoRA line of work addressed and every major engine now implements. You keep adapters unmerged and compute x·Wᵀ + (x·Aᵀ)·Bᵀ·(α/r) at inference, where the extra work is two skinny GEMMs, negligible in FLOPs and awkward in shape. You batch across heterogeneous adapters , since a batch contains requests using different ones, which makes the LoRA term a grouped operation where you segment the batch by adapter and apply each group’s matrices, a gather-GEMM-scatter that is structurally the same problem as MoE’s grouped GEMM. You page the adapter weights , because with hundreds of adapters and only some active, adapter memory becomes another paged pool with its own allocator and eviction, which is the KV cache’s problem again and worth solving with the same machinery. And you include the adapter in the prefix cache key (Chapter 17), because two requests with identical tokens and different adapters have different KV, and omitting that is a correctness and isolation bug.

Performance-wise, unmerged multi-adapter serving costs a few percent against the merged singleadapter case and buys the ability to serve hundreds of fine-tunes from one set of base weights, which is usually a far larger economic win than the few percent.

Multimodal inputs

A vision-language model prepends encoded image, audio, or video tokens to the text sequence. Structurally that’s preprocessing on CPU or GPU, decoding and resizing and normalising and tiling, where modern models use dynamic resolution so one image becomes a variable number of patches. Then encoding with a vision transformer to produce patch embeddings, projecting into the language model’s embedding space, splicing the projected embeddings into the token embedding sequence at placeholder positions, and finally prefill and decode as usual.

What that does to the engine is where the work is.

Prefill cost decouples from token count , since an image may expand to thousands of tokens and the encoder is a separate model with its own compute profile, so scheduler cost models based on text token counts systematically under-predict.

Preprocessing is a real

bottleneck , because image decode and resize on the CPU can dominate TTFT for image-heavy traffic, which means that work belongs in a separate process pool overlapped with GPU execution rather than inline in the scheduler thread.

Encoder outputs are cacheable , since the same image sent twice produces the same embeddings, so a content-hashed cache of encoder outputs pays for itself immediately in multi-turn conversations about one image.

Prefix caching needs care , because the cache key has to cover the image content rather than only the placeholder tokens, or two different images with the same prompt text collide, which is a serious correctness failure.

Memory spikes , since the encoder’s activations for a batch of high-resolution images can rival the language model’s and they arrive in bursts. Bound them explicitly, or a burst of image requests will OOM a server that’s been stable for weeks.

Both features share a lesson worth generalising. The serving engine’s core abstractions, paged pools and grouped GEMMs and content-addressed caches and cost models, get reused rather than replaced when new capabilities arrive. An engine built around those absorbs LoRA and multimodality with modest work, and one built around the idea that a batch is a rectangle of text tokens doesn’t.

Key Concept

Multi-adapter LoRA serving keeps adapters unmerged and applies them as a grouped skinny GEMM over an adapter-segmented batch, with adapter weights in their own paged pool, which is the same machinery as MoE grouped GEMM and paged KV. Multimodal inputs add an encoder with its own cost profile, expensive preprocessing that has to be overlapped, and cacheable encoder outputs. Both have to be part of the prefix-cache key, or you’ll serve one request’s context to another.

Exercises

  1. For a 70B model with LoRA rank 16 applied to all attention projections, compute the adapter size and the extra FLOPs per token. What fraction of a decode step is that?

  2. Design the batching layout for a step containing requests using four different adapters. What does the grouped operation look like, and how do you avoid padding waste?

  3. An image expands to 2,600 tokens. Explain how that breaks a scheduler cost model calibrated on text, and propose a fix.

  4. Build: implement a content-hashed cache for vision encoder outputs and measure TTFT for a multi-turn conversation about one image, with and without the cache.
