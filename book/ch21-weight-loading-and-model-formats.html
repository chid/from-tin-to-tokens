Part V: Model Execution

Weight Loading and Model Formats

Model formats

SafeTensors is the default for open model weights, and it’s about as simple as a format can be. An 8- byte little-endian u64 giving the header length N , then N bytes of JSON header describing each tensor’s dtype, shape, and byte range, then the data buffer with tensors laid out contiguously. It was designed for safety, since there’s no code execution unlike pickle, and for zero-copy loading, since the data buffer is memory-mappable and tensors are byte-range views. Large models ship as multiple shards with an index file mapping tensor names to shard files.

GGUF from llama.cpp is a self-contained file with quantised weights, full metadata, and the tokeniser, designed so that one file plus one binary is a complete deployment. Excellent for edge, less interoperable with the training ecosystem.

PyTorch checkpoints use Python pickle, which executes arbitrary code on load. Don’t load untrusted ones, convert to SafeTensors first.

Parsing SafeTensors, defensively

struct TensorInfo {
    dtype: String,                 // "F16", "BF16", "F32", "F8_E4M3", ...
    shape: Vec<usize>,
    data_offsets: (usize, usize),  // [start, end) within the data buffer
}

The parsing steps are mechanical and the validation is what matters, because every malformed field becomes an out-of-bounds GPU access later. Read the 8-byte length and reject absurd values before allocating anything. Parse the JSON header. Then for every tensor, check that product(shape) × dtype_size == end − start , that start ≤ end , and that end lies within the file, so that a truncated download or a corrupted shard fails here, on the host, rather than as a VM fault on the device. Check offsets are in range and, ideally, that the tensor set matches the architecture you expect.

Add an integrity check for production, hashing the file against a manifest. A checkpoint corrupted in transit produces a model that generates plausible-looking garbage, which is the hardest failure to diagnose from the output alone.

Data types you’ll actually encounter

A loader has to handle at least FP32, FP16, BF16 , FP8 in both E4M3 and E5M2, and integer formats with separate scale tensors.

BF16 deserves specific attention, because it’s what most modern checkpoints are stored in and it gets far less coverage than FP16. BF16 has 8 exponent bits and 7 mantissa bits, giving it FP32’s dynamic range with a quarter of the precision, while FP16 has 5 exponent bits and 10 mantissa bits, more precision and far less range.

Three consequences follow for the loader and the kernels beneath it.

BF16 to FP16 conversion can overflow. BF16 represents values up to about 3.4e38 while FP16 saturates at 65,504, and models trained in BF16 do contain weights and, more often, activations outside FP16’s range. Converting a BF16 checkpoint to FP16 without checking is a real source of inf and NaN in the first forward pass.

BF16 to FP32 is trivial in one direction , since BF16 is the top 16 bits of an FP32. Truncating is cheap and rounding to nearest even is correct.

Accumulate in FP32 regardless. Both are storage formats, so every reduction, RMSNorm sums and attention scores and GEMM accumulation, should accumulate in FP32 or higher, and the storage format shouldn’t change that.

If your kernels are FP16 and your checkpoints are BF16, the decision to convert at load time is a real one with a quality consequence, so measure it against the f64 oracle of Chapter 36 rather than assuming it’s free.

Tensor-parallel slice planning

For multi-GPU inference, weights get split across GPUs Megatron-style, and the notation trips almost everyone up at least once, so let’s fix it here and use it consistently for the rest of the book.

Store weights in PyTorch’s nn.Linear convention, where a weight matrix has shape (out_features, in_features) and y = x · Wᵀ .

Column-parallel splits the output features, which in the stored layout is axis 0 , the rows. Each rank gets a contiguous range of rows, and because rows are contiguous in memory each rank’s slice is one contiguous byte range. Easy.

Row-parallel splits the input features, which in the stored layout is axis 1 , the columns. Each rank gets a column range from every row, so its slice is strided , out_features separate byte ranges with gaps between them.

The names come from the mathematical matrix in y = xW , where they refer to columns and rows respectively, and they refer to the opposite axis of the stored transposed matrix. That mismatch is the single most common source of confusion in TP loaders, and it is entirely possible to carry the inconsistency across two chapters of your own codebase without noticing. Pick the stored-layout convention, write it down, and use it everywhere.

The strided case is the hard part of TP loading, and you have three options. Scatter-read does one read per row, which is correct and catastrophically slow since out_features can be tens of thousands. Rowcoalescing reads a contiguous window covering several rows’ slices and discards the parts belonging to other ranks, trading read amplification, a factor of TP size in the worst case, for large sequential reads, and it’s usually the right answer. Offline re-layout pre-shards the checkpoint so each rank’s slice is contiguous, which is fastest at load time and costs you a conversion step plus TP-degree-specific artefacts.

For a system that reloads frequently, offline re-layout wins. For one that loads once at startup, coalescing is enough and avoids maintaining per-TP-degree copies of a 400 GB checkpoint.

Getting the bytes to the GPU

Three mechanisms, in increasing order of sophistication.

Buffered read then copy reads into host memory and copies to VRAM. Simple, double-buffers through the page cache, wastes bandwidth and pollutes the cache.

Direct I/O with O_DIRECT bypasses the page cache, which matters because weights are read once and never re-read, so caching them evicts everything else on the node for no benefit. The requirement is alignment, since the buffer address, file offset, and length all have to be block-aligned, typically to 4,096 bytes. Tensors don’t start on block boundaries, so the pattern is an aligned_read_window , expanding the tensor’s range to the enclosing aligned window, reading the window, and skipping the prefix bytes.

DMA straight to VRAM uses a large BAR and a DMA engine, SDMA on AMD, to move data from a host staging buffer into device memory without the CPU copying it, overlapping transfer with compute on other layers. This is where a from-scratch loader can beat a naive framework loader substantially.

Overlapping load with compute

For a 400 GB checkpoint, loading takes minutes rather than seconds and dominates cold-start time, which matters enormously for autoscaling. The pipeline starts reading layer i ’s weights while the layers already resident begin work, for prefill of the first request or for warmup, with a per-layer resident flag the dispatch path waits on.

That synchronisation has to be real. Dispatching a layer whose weights are still in flight reads whatever was in that VRAM beforehand, so a per-layer completion signal checked before the first dispatch touching those weights is the minimum.

Rust patterns for weight loading

Parse once into a validated TensorDescriptor { name, dtype, shape, offsets } so everything downstream consumes the validated form and the “is this shape sane” question gets asked in exactly one place. Use memmap2 for the file and explicit copies to VRAM, since mapping gives cheap random access to the header and tensor ranges while the copy stays explicit because you want to control placement. Provide typed views through as_mut_slice_of::<T>() on a DeviceBuffer , with the same temporal safety contract as Chapter 6.

And fail loudly. A loader that silently zero-fills a missing tensor produces a model that runs and is wrong, so a missing tensor, shape mismatch, or dtype surprise should each be a hard error naming the tensor.

Key Concept

Weight loading is a systems problem rather than a maths problem. The format decides how you parse metadata, the TP plan decides how you slice, Direct I/O keeps the page cache clean, and DMA with perlayer overlap keeps cold start bounded. Fix one axis convention for TP slicing and use it everywhere, where the stored layout is (out_features, in_features), column-parallel splits axis 0 contiguously, and rowparallel splits axis 1 and is strided. Validate every tensor’s size on the host, because the alternative is an out-of-bounds read on the device.

Exercises

  1. A weight of shape (8192, 4096) in BF16 is row-parallel split across 8 ranks. How many byte ranges does rank 3 need, and how large is each? What is the read amplification if you coalesce 16 rows at a time?

  2. Explain why BF16 to FP16 conversion can overflow but BF16 to FP32 cannot. Write the check a loader should perform and decide what it should do on failure.

  3. Build: write a SafeTensors parser with full validation. Feed it a truncated file, a file with an inconsistent shape, and a file with overlapping tensor ranges, and confirm each produces a distinct, clear error.
