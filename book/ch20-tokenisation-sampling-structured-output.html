Part IV: The Serving Engine

Tokenisation, Sampling, and Structured Output

CHAPTER 20 · TOKENISATION, SAMPLING, AND STRUCTURED OUTPUT

The layers at the very top and very bottom of a request are easy to skip in a book about kernels, and they’re responsible for a surprising share of production bugs and rather more latency than anyone expects. This chapter covers the path from text to token IDs, the path from logits back to text, and the machinery for constraining what the model is allowed to say.

Tokenisation

Modern LLMs use subword tokenisation, almost always byte-level BPE in the GPT, Llama, and Qwen lineage or SentencePiece Unigram elsewhere, and four properties matter to an engine.

Byte-level fallback means no unknown tokens. Byte-level BPE operates on UTF-8 bytes, so any input encodes and there’s no out-of-vocabulary case to handle, which removes a whole class of errors.

Tokenisation isn’t a bijection over text fragments. The same string can tokenise differently depending on what precedes it, which is why you can’t tokenise a conversation turn by turn and concatenate. You have to apply the chat template to the full conversation and tokenise the result, or the prefix you compute won’t match the prefix another request computes for the same text, destroying prefix-cache hit rate and, worse, feeding the model a token sequence it never saw in training.

Chat templates are part of the model. The mapping from a structured message list to a token sequence, with its role markers and system prompt placement and generation prompt and tool-call syntax and, for reasoning models, thinking delimiters, ships with the model as a Jinja template in the tokeniser config. Implementing it by hand is a reliable way to produce a model that’s subtly worse than everyone else’s copy of the same weights.

Special tokens must never come from user text. If a user’s message contains the literal string for your end-of-turn token and your tokeniser encodes it as that special token, the user can forge role boundaries. Encode user content with special-token handling disabled and insert control tokens structurally.

Incremental detokenisation

Streaming means converting token IDs back to text one token at a time, and the naive implementation is wrong in an interesting way. A single token can be a partial UTF-8 sequence or a partial grapheme cluster, so emitting it shows the client a replacement character, and a multi-byte emoji or CJK character can span several tokens.

The correct approach buffers undecodable bytes until they form a complete character, and it also holds back text that might participate in a stop string. Take a stop sequence of "</answer>" . On seeing "</ ans" you must not stream it, because if the next tokens complete the stop sequence then that text should never have been emitted at all.

So the detokeniser is a small state machine with a hold-back buffer, flushing only what’s both valid UTF-8 and not a prefix of any active stop string. Get it wrong and you produce bugs that appear only for nonEnglish text or only near stop sequences, which is to say bugs that reach production.

Detokenisation isn’t free either. At high aggregate token rates a naive implementation that re-decodes the whole sequence each step is O(n²) and will saturate a host core long before the GPU is busy.

Sampling

After the LM head produces logits over the vocabulary, 151,936 entries for Qwen3, the sampler picks a token. Greedy takes the argmax. Temperature divides logits before softmax, sharpening below 1 and flattening above. Top-k restricts to the k highest-probability tokens. Top-p, or nucleus, restricts to the smallest set whose cumulative probability exceeds p , adapting to the distribution’s shape. Min-p restricts to tokens with probability at least p times the maximum, which is more stable than top-p at high temperature. And repetition, presence, and frequency penalties modify logits based on what’s already been generated.

Order matters and it’s a genuine source of cross-engine mismatch, since applying penalties before or after temperature, or top-k before or after top-p, gives different distributions. Engines document their order, and if you’re matching another engine’s outputs you match its order.

Sample on the device. Sampling is often described as happening on the host and therefore off the critical path, which is wrong on both counts for a modern engine. For a batch of B sequences the logits tensor is B × 151,936, which at FP32 and batch 64 is 39 MB, and copying that to the host every token costs more than the sampling does. Worse, it serialises, since the GPU idles while the host decides and then has to be re-fed. Production engines run temperature, penalties, top-k and top-p filtering, and the categorical draw as GPU kernels, transferring only the sampled token IDs, a few hundred bytes. Only the stop-condition check and detokenisation need the host, and both work on token IDs.

The tricky part of on-device sampling is that every sequence in the batch can have different parameters, and the standard solution passes parameter vectors and has the kernel apply per-row parameters, with fast paths for the common case where all rows are greedy or all share settings.

Structured output

Plenty of applications need output conforming to a JSON schema or a regex or a grammar, and doing that by prompting and retrying is expensive and unreliable, while doing it in the engine is exact.

The mechanism is constrained decoding . At each step you compute the set of tokens that could legally extend the output and set every other logit to −∞ before sampling, so the model still chooses among valid tokens according to its own distribution and simply can’t choose invalid ones.

The engineering problem is that the constraint is over characters while decoding is over tokens , and a single token can span several grammar symbols. Done naively, testing all 152K tokens against the grammar at every step costs more than the model forward pass.

What makes it fast is compiling the grammar to an automaton and precomputing, per automaton state, the bitmask of allowed tokens, so applying the constraint at decode time is a mask lookup and an elementwise operation. Masks get cached across requests sharing a schema, which is the common case in production, mask computation overlaps the forward pass since the next state depends only on the token just emitted, and token-boundary ambiguity gets handled by tracking a set of automaton states rather than one, or by restricting to a canonical tokenisation.

XGrammar, Outlines, and Guidance are the widely used implementations, and XGrammar is integrated into vLLM, SGLang, and TensorRT-LLM with near-zero overhead masking for typical JSON schemas.

Two production cautions. Constrained decoding guarantees syntactic validity, not semantic correctness, so a schema-valid object can still be nonsense. And over-constraining hurts quality, because forcing a token the model finds very unlikely pushes it off-distribution, and the usual symptom is degenerate repetition. Where you can, constrain to a grammar the model was trained to produce.

Determinism and reproducibility

Same prompt, same seed, same output is a reasonable expectation and, on a standard inference server, false. The reason isn’t floating-point non-associativity in the abstract, it’s batch invariance .

Most GPU kernels, matmul and RMSNorm and softmax and attention, change their reduction strategy with the shape of the work, so a kernel processing a batch of 4 may split reductions differently than the same kernel on a batch of 32, producing different rounding. Since a serving engine’s batch composition depends on what other requests happen to be in flight, your result depends on other users’ traffic. Same prompt, same seed, different answer.

The fix, formalised by Thinking Machines Lab in 2025 and since implemented in SGLang and elsewhere, is batch-invariant kernels , constraining each kernel to one reduction strategy independent of batch size through fixed split counts, fixed-size reduction trees, and data-parallel rather than split-K matmuls. With those in place, output becomes bitwise reproducible under dynamic batching, at a reported cost of roughly 25 to 60% end-to-end. Thinking Machines Lab measured around 60% overhead on an 8B model, and SGLang’s integration reports a range depending on attention backend that falls to about a third once graph capture is re-enabled over the batch-invariant kernels.

Worth paying for reinforcement learning from model outputs, where train-inference mismatch silently corrupts the objective, for debugging, since a bug you can’t reproduce is a bug you can’t fix, and for regression testing, audit, and regulated deployment. Not worth paying for ordinary user-facing serving, where that overhead buys nothing anyone perceives.

Determinism also needs the obvious hygiene, a fixed seed per request rather than a global RNG shared across a batch, sampling parameters that don’t depend on batch composition, and, if you speculate, a fixed speculation depth, since acceptance changes the reduction shapes too.

Key Concept

Tokenisation and detokenisation are stateful and easy to get wrong. Tokenise whole conversations through the model’s chat template, never encode user text as special tokens, and stream through a hold-back buffer that respects UTF-8 boundaries and stop strings. Sample on the device, because a batch of 152Kwide logits is far too large to ship to the host every token. Constrained decoding gives exact structural validity through precompiled automaton masks. And reproducibility requires batch-invariant kernels, because default kernels change their reduction strategy with batch shape and therefore make your output depend on other users’ traffic.

Exercises

  1. Give a concrete example where tokenising a conversation turn by turn and concatenating produces a different token sequence than tokenising the templated whole. What does that do to prefix-cache hit rate?

  2. Design the hold-back logic for a streaming detokeniser with stop sequences ["\n\n", "</answer>"] . What’s the maximum number of characters that can be held back, and how do you flush correctly at end of stream?

  3. Compute the per-token host transfer cost of CPU sampling for batch 64 and vocabulary 151,936 in FP32, and compare with transferring sampled IDs. At what batch size does CPU sampling exceed a 2 ms decode step?

  4. Build: implement top-k and top-p filtering as a GPU kernel supporting per-row parameters, and verify against a host reference for exact equality on the selected candidate set.

  5. Build: demonstrate batch-dependence by running the same prompt at batch 1 and batch 32 with greedy sampling and finding the first token position where they diverge, then explain the divergence in terms of a specific reduction.
