Introduction

What this book is

Somewhere between a trained model and a person waiting for an answer sits a piece of software that nobody outside the field thinks about much, and it decides almost everything about whether the product is any good. It sets how fast the words appear, how many people you can serve at once, and what each one of those answers costs you. This is a book about building that software.

It covers the whole stack, starting at the driver interface where you’re writing ioctl structures by hand and finishing at an HTTP endpoint serving thousands of concurrent users. Along the way you’ll build attention kernels, a paged KV cache, a scheduler, multi-GPU collectives, a quantisation pipeline, and the correctness apparatus that proves any of it works.

The book is written for people who want to understand inference properly, whether you’re evaluating engines for a deployment, building one, or just trying to work out why this problem is so much harder than it looks. Concepts come first and implementations follow, because the implementations change every eighteen months and the concepts don’t.

Rust is the implementation language throughout, and the reason is more specific than “memory safety.” At this layer a bad pointer doesn’t crash your process, it can take down a node, so the boundary between the unsafe code that talks to the kernel and the safe code above it turns out to be the central architectural decision rather than a stylistic one. That’s Chapter 3. Rust proficiency helps but isn’t required, and every pattern transfers directly to C++ or CUDA C.

How numbers are used in this book

Performance engineering is full of numbers that get repeated until they stop being true, so it’s worth saying up front what kind of number you’re looking at whenever one appears.

Spec numbers are labelled as spec numbers. When the text says an MI355X has 8 TB/s of HBM bandwidth, that’s a vendor peak figure and the text says so. You will never measure it.

Measured numbers carry their conditions. Every measured figure states the hardware, the workload, and where it came from, because a number without conditions is marketing rather than engineering. Measurements attributed to mainarch were taken on an 8×MI355X (gfx950) node running the stack this book describes, they’re reproducible from that repository’s benchmark harness, and they’re reported here including the places where the stack loses. A benchmark you can’t lose isn’t a benchmark.

Derived numbers show their arithmetic. Where the book works out a KV cache size or a bandwidth floor, the expression is written out so you can run it against your own model and your own hardware. Most of the surprising results in inference turn out to be one line of arithmetic away from being obvious, which is exactly why so many of them get quoted wrong.

Third-party results are cited to the paper or documentation that produced them, and Appendix F has the full list. Where the literature disagrees, or where a widely repeated figure is simply wrong, the book says so instead of picking whichever version is convenient.

The state of the art as of 2026

LLM inference has consolidated fast. Four engines and one kernel library dominate the open landscape, and they’ve converged on a shared set of ideas while differentiating on maturity, hardware, and what they choose to optimise.

vLLM is the most widely deployed open-source serving engine. Its V1 engine, shipped in 2025 and now the default, is worth studying as an architecture in its own right, because it represents the current consensus about how one of these should be built. The scheduler runs asynchronously from model execution, a persistent batch diffs its input tensors between steps rather than rebuilding them, torch.compile is on by default, and piecewise CUDA graphs wrap the parts of the model whose shapes don’t move.

SGLang made prefix reuse automatic with RadixAttention, invested heavily in fast structured generation, and has become a common choice for very large MoE models and disaggregated deployments.

TensorRT-LLM is NVIDIA’s engine, with kernels co-designed alongside each GPU generation and frequently written before that generation is public. Increasingly it serves as a kernel provider for other engines as well as a runtime in its own right.

llama.cpp owns local, edge, and CPU inference, with the GGUF format and genuinely broad hardware coverage. Its server has supported continuous batching across parallel slots for years now, so the old line about llama.cpp not being able to batch is several years out of date.

FlashInfer is a JIT-compiled kernel library for attention and sampling, used as a backend by both SGLang and vLLM on NVIDIA hardware.

Underneath all five sit the same load-bearing ideas, which is the good news for anyone learning this material. Paged KV cache management, continuous batching, FlashAttention-style tiling, grouped-query attention, speculative decoding, and prefill/decode disaggregation show up everywhere, and the differences between engines are differences of implementation rather than approach.

The interesting work in 2026 has moved elsewhere. Sparse and hybrid attention have made milliontoken context economical rather than merely possible. Four-bit numerics are arriving for weights and, more tentatively, for the KV cache. Persistent megakernels and GPU-driven collectives are attacking host overhead from opposite ends. And disaggregated, KV-centric serving has become the default topology at cluster scale. All four are covered here, with an honest account of what’s production-ready and what isn’t.

What this book covers

Bottom-up, the stack looks like this.

The hardware layer covers GPU architecture, the driver interface, device memory, and command dispatch. Attention and the KV cache covers the attention variants (MHA, GQA, MQA, MLA), FlashAttention, FlashDecoding, KV quantisation, paged KV, memory management, and the long-context techniques that make a million tokens affordable. The serving engine covers continuous batching, scheduling, prefix caching, chunked prefill, speculative decoding, and the tokenisation and sampling layers that bracket every request. Model execution covers weight loading, the decode layer, the autoregressive loop, mixture-of-experts, kernel fusion, adapters, and multimodal inputs. Multi-GPU and distributed covers the interconnect fabric, collectives, the parallelism strategies, and disaggregated serving. Quantisation and compression covers weight quantisation and KV cache compression. The hardware landscape covers NVIDIA against AMD, specialised silicon, and edge deployment. And proof, testing, and production covers correctness validation, performance measurement, determinism, and the path to a system you can actually operate.

How to read this book

Nine parts, moving from the hardware up to the system.

  • Part I, Foundations. Why inference is different, the ecosystem, why Rust.

  • Part II, The Hardware Layer. GPU architecture, the driver interface, device memory, command queues.

  • Part III, Attention and the KV Cache. Attention variants, FlashAttention, FlashDecoding, KV quantisation, paged KV, memory management, long-context attention.

  • Part IV, The Serving Engine. Continuous batching, scheduling, prefix caching, chunked prefill, speculative decoding, tokenisation and sampling.

  • Part V, Model Execution. Weight loading, the decode layer, the autoregressive loop, MoE, kernel fusion and graphs, adapters and multimodal.

  • Part VI, Multi-GPU and Distributed. The interconnect fabric, collectives, parallelism strategies, disaggregated serving.

  • Part VII, Quantisation and Compression. Weight quantisation, KV cache compression.

  • Part VIII, The Hardware Landscape. NVIDIA against AMD, specialised silicon, edge inference.

  • Part IX, Proof, Testing, and Production. Correctness validation, performance measurement, determinism, building a production stack.

You don’t have to read it in order. Parts I and II are the hardware story, Parts II and III the kernel story, Part IV the serving story, Parts V and VI the systems story, Part VII quantisation, and Part IX production. The appendices cover Rust patterns for GPU programming, GPU command interfaces, code object loading, an ecosystem reference, a glossary, and a bibliography.

A note on examples

Concepts come first here, then real implementations to make them concrete. The examples come from a handful of projects. vLLM and SGLang supply the serving-engine material, FlashAttention and FlashInfer the attention kernel algorithms, llama.cpp the edge and quantisation work, and mainarch, an inference stack written in Rust that talks straight to the AMD kernel ABI, supplies the low-level systems material along with the AMD-side measurements.

mainarch shows up most in the hardware and execution chapters, partly because low-level Rust is illustrative and partly because a system with no runtime underneath it makes the mechanism visible in a way that a system built on CUDA can’t. The book doesn’t reproduce project documentation. Concepts are taught generically and code appears in service of the concept rather than the other way round. Where mainarch hasn’t won, and large-message collective bandwidth is the clearest example, the book says so, because the shape of a loss teaches as much as the shape of a win.

Conventions

Code examples are in Rust unless noted. Rust’s type system does real work in several chapters, particularly around the unsafe boundary, Drop semantics, and newtype wrappers, and the book explains those patterns where they first appear.

Where hardware specifics matter, and they matter often, the two running examples are AMD CDNA4 (gfx950, MI355X) and NVIDIA Hopper (H100), with Blackwell noted where it diverges. Every number states which architecture it belongs to.

Model-specific details use Qwen3-235B-A22B as the running example. That’s 94 layers, hidden size 4096, 64 query heads and 4 KV heads of dimension 128, 128 experts with top-8 routing, expert intermediate size 1536, and a vocabulary of 151,936. Two releases of this model exist and they differ precisely where it matters for inference. The original from April 2025 uses rope_theta = 1e6 with 40,960 native positions, while the Instruct-2507 refresh uses rope_theta = 5e6 with 262,144 native positions and a documented path to a million tokens through dual-chunk attention. Whenever the book quotes a Qwen3 constant it names which release.

Key concept boxes summarise each chapter’s load-bearing idea. If you remember nothing else from a chapter, remember that.

British spelling throughout, except in code and identifiers, which keep whatever their upstream authors chose.
