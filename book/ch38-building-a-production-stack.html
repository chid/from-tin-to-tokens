Part IX: Proof, Testing, and Production

Building a Production Stack

The API surface

The de facto standard is the OpenAI-compatible HTTP API, and adopting it means every existing client works without modification, which is worth more than any design improvement you might make instead.

POST /v1/chat/completions is the primary endpoint, taking model, messages, sampling parameters, tools, and response format. POST /v1/completions is legacy text completion. GET /v1/models reports what’s served.

Streaming happens over Server-Sent Events, one delta per token, terminated by a sentinel, and it isn’t a feature bolted on afterwards because it changes the error model. You’ve already sent a 200 before you know whether generation will succeed, so mid-stream failures have to be signalled in-band.

Cancellation matters more than it sounds. When a client disconnects the server has to stop generating and free the KV blocks immediately , which is easy to get wrong behind a proxy that buffers, and getting it wrong wastes a large fraction of a busy server’s capacity on abandoned requests.

In a Rust stack, axum with tokio for the API layer and a channel to the synchronous engine thread is the natural structure (Chapter 3), and the model step stays off the async runtime’s worker pool.

Observability

Metrics for Prometheus should cover throughput as requests per second and prompt and generated tokens per second, latency as histograms rather than averages for TTFT and TPOT and end-to-end, queue depth and waiting time, KV cache state including blocks used and free and prefix-cache hit rate and preemptions, batch composition including running sequences and prefill tokens per step, GPU utilisation and memory and clocks and temperature and ECC errors, and errors by class.

The two most diagnostic and most often missing are prefix-cache hit rate , which predicts prefill load, and preemption rate , which tells you your admission policy is wrong before users do.

Tracing through OpenTelemetry wants a span per request with child spans for queueing, prefill, each decode phase, and detokenisation, and in a disaggregated deployment the trace has to cross the prefill and decode boundary or you can’t attribute latency at all.

Structured logging wants request IDs that appear in client-facing errors, so a user’s report maps to a trace.

Error handling

Malformed requests get a 400 with a specific message, validated before admission. Context too long gets a 400 with the actual limit and the actual token count. Overload gets a 429 with Retry-After , promptly, because queueing beyond capacity converts a throughput problem into universal latency failure. OOM during decode shouldn’t happen if admission and watermarks are right, and when it does you preempt rather than fail, and alert. A GPU fault, a device reset or a hung queue, kills every in-flight request on that device, so you detect it with a watchdog on the completion signal, fail those requests

explicitly, drain, and restart the worker, because a server that hangs silently on a wedged GPU is worse than one that crashes. And a corrupt checkpoint gets caught by hash verification at load, refusing to serve.

Deployment and Kubernetes

The standard shape starts with a container holding the runtime and engine, with weights mounted from a volume or pulled from object storage at startup, since baking 400 GB into an image makes the image unusable.

Model loading dominates cold start, minutes for large models, and it’s the central operational constraint. Mitigations are fast local NVMe caches, parallel shard loading, memory-mapped weights shared between processes, and keeping warm spare replicas.

Health probes need to be two different things. A readiness probe true only when weights are loaded and a test forward pass has succeeded, and a liveness probe that fails when the engine is wedged. Conflating them routes traffic to a loading pod or lets a wedged pod persist.

Graceful shutdown on SIGTERM stops accepting, finishes in-flight requests, then exits, with a termination grace period longer than your longest generation or Kubernetes kills mid-stream.

Device plugins request GPUs, and topology-aware scheduling puts a TP=8 replica on eight GPUs of the same node with the right fabric connectivity, where getting it wrong silently costs a large fraction of collective bandwidth.

Autoscaling has to use the right signal, and GPU utilisation is a poor one because a memory-bound decode loop shows high utilisation while doing nothing. Scale on queue depth, TTFT percentile, or KV cache pressure, and account for cold start, since an autoscaler with a 3-minute model load and a 30second reaction time is permanently behind the traffic.

Rollout has to account for model and engine upgrades changing outputs, so canary a small traffic fraction and compare quality metrics rather than only error rates before proceeding.

Multi-tenancy

Per-tenant quotas on rate, concurrency, and context length. Fair scheduling so no tenant monopolises (Chapter 16). Prefix cache isolation where tenants are mutually untrusting, since shared caches leak timing information about others’ prompts (Chapter 17). And adapter isolation, since the adapter has to be part of every cache key (Chapter 26).

Security

Never load pickle checkpoints from untrusted sources. Verify weight integrity with hashes against a manifest. Treat the prompt as untrusted input at the tokenisation boundary, since special tokens must not be forgeable from user text (Chapter 20). Bound resource consumption per request with maximum context, maximum output, and maximum images, because without those one request can consume a node. And don’t log prompts and completions by default, since they’re user data and frequently sensitive.

What to build and what to borrow

Build what’s your differentiator, meaning the compute path with its device interface and kernels and memory management and collectives, the KV manager, and the scheduler if your workload is unusual.

Borrow everything else. The HTTP framework, the observability stack, container orchestration, the model format, the tokeniser implementation, and the structured-output grammar compiler are each a project in their own right and none of them will make your system faster.

The honest assessment

Most teams should use an existing engine. The compute path is where custom engineering pays and it’s also the hardest part to get right, while the serving layer is equally hard and much less differentiating.

The hybrid that works is to build the compute path where you have a genuine advantage, unusual hardware or an extreme latency requirement or a technique nobody supports, and integrate it beneath an existing engine’s serving layer through its backend or connector interfaces. Custom performance where it matters, mature infrastructure where it doesn’t.

Key Concept

A production stack is more than a compute path. It needs an OpenAI-compatible API with correct streaming and cancellation, metrics as histograms with prefix-cache hit rate and preemption rate among them, tracing that crosses process boundaries, explicit handling for overload and GPU faults, and a Kubernetes deployment whose readiness probes and grace periods and autoscaling signals account for multi-minute model loads. Build the compute path, borrow the rest.

Exercises

  1. Design the health-probe strategy for a server with a 4-minute model load and generations up to 5 minutes. Specify readiness, liveness, grace period, and what each returns during load, steady state, and shutdown.

  2. Explain why GPU utilisation is a poor autoscaling signal for decode and propose a composite signal with thresholds.

  3. A shared prefix cache leaks timing information between tenants. Quantify what an adversary learns and give two mitigations with their costs.

  4. Build: implement an OpenAI-compatible streaming endpoint with cancellation. Verify with a client that disconnects mid-stream that KV blocks are freed within one decode step.
