Part I: Foundations

The Inference Ecosystem

Nobody builds an inference stack in a vacuum, and it would be foolish to try. The ecosystem matured quickly after 2023, converged on a shared set of ideas, and then differentiated on implementation, hardware, and priorities. This chapter walks the landscape so that later chapters can point at these systems as examples instead of explaining them from scratch each time.

vLLM

vLLM (Kwon et al., SOSP 2023) is the most widely used open-source inference engine, and its defining contribution was PagedAttention , which treats the KV cache as a paged virtual memory system with logical-to-physical block mapping, on-demand allocation, and copy-on-write sharing. That solved the fragmentation problem that had been quietly capping everyone’s concurrency, and it’s what makes continuous batching practical at high occupancy.

The V1 engine from 2025 is now the default and repays study as an architecture, because it represents the current consensus about how to build one of these. The scheduler runs asynchronously from model execution, so scheduling for step t+1 overlaps GPU work for step t . A persistent batch caches input tensors across steps and applies only the diff each iteration rather than rebuilding them. torch.compile is on by default, with piecewise CUDA graphs capturing the model around the attention kernels, graph capture where shapes are static and eager execution where they aren’t. Prefix caching is on by default and chunked prefill is the default scheduling mode.

vLLM is the reference implementation for most of the serving-engine material in this book. It targets NVIDIA primarily, with mature ROCm support and backends for TPU and other accelerators.

SGLang

SGLang (Zheng et al., 2024) introduced RadixAttention , a radix tree over KV cache blocks that gives you automatic prefix caching. When requests share a prefix, and in production they share prefixes constantly, SGLang reuses the computed KV blocks without recomputation and without anyone asking it to.

It also pushed hard on structured generation , constraining output to a JSON schema or grammar without leaving the engine, which is why it’s popular for agentic workloads where the output has to be machine-parseable. Chapter 20 covers how that’s made cheap.

Through 2025 and 2026 SGLang became a common choice for very large MoE models and disaggregated deployments, and it carries first-class support for the sparse attention backends of Chapter 14 on both NVIDIA and AMD hardware.

TensorRT-LLM

NVIDIA’s engine, built on the TensorRT compiler framework, and its defining characteristic is deep hardware co-design. Kernels are written alongside each GPU generation, often before that generation is publicly available.

It popularised in-flight batching , NVIDIA’s name for the iteration-level scheduling Orca introduced in 2022, and has the most mature support for NVIDIA-specific features, FP8 on Hopper, NVFP4 on Blackwell, and heavily tuned speculative decoding. Increasingly its kernels get consumed by other engines rather than only by its own runtime. The trade-off is that it runs on NVIDIA hardware and nothing else.

llama.cpp

llama.cpp owns local, edge, and CPU inference. It began as a C/C++ port of LLaMA and grew into a full engine with the GGUF format, a self-contained file holding quantised weights, metadata, and tokeniser, plus genuinely broad hardware support across CPU (AVX2, AVX-512, NEON, SVE) and GPU (CUDA, Metal, Vulkan, ROCm, SYCL), a wide family of quantisation formats from two bits to eight, and partial GPU offload that puts some layers on the GPU and runs the rest on the CPU.

One correction to a claim that still gets repeated a lot. llama-server does implement continuous batching across parallel slots, controlled by --cont-batching , which is on by default, and --parallel for the slot count. It isn’t a datacentre-scale scheduler, there’s no preemption or priority or disaggregation, but the line about llama.cpp being unable to batch stopped being true years ago.

FlashInfer

FlashInfer is a kernel library for attention, sampling, and related primitives, built as shared infrastructure rather than as an engine. It provides prefill, decode, and append attention kernels with paged KV, GQA, and low-precision support, JIT-compiled for the shape you actually have.

One point of accuracy, because this one is widely gotten wrong. Upstream FlashInfer is CUDA-only. It isn’t a vendor-abstraction layer. AMD maintains a separate ROCm port in the ROCm/flashinfer repository, under active development and not yet at feature parity, and engines running on AMD hardware generally reach for AITER, Composable Kernel, or Triton attention backends instead. Crossvendor portability is real, but it comes from engines maintaining multiple backends rather than from one library spanning both.

The Rust ML ecosystem

Young, growing, and worth knowing about even though a from-scratch stack uses almost none of it.

Candle from Hugging Face is a minimalist framework with CUDA, Metal, and CPU backends, built for serverless inference where a small binary and no Python runtime matter. Burn is a fuller deep learning framework with multiple backends and its own kernel-authoring layer, CubeCL. mistral.rs is a Rust inference engine built on Candle, with GGUF support, paged attention, and an OpenAI-compatible server. And mainarch is a Rust stack that talks straight to the AMD kernel ABI with no ROCm, HIP, or HSA runtime beneath it, which is the low-level example running through this book.

The general shape is that Rust now gives you the language, the tooling, and increasingly the framework layer, while the GPU kernels themselves are still written in a C dialect and compiled by the vendor toolchain or emitted by a Rust-hosted kernel DSL. Nobody’s writing gfx950 MFMA schedules in safe Rust yet.

DeepSpeed-FastGen and LMDeploy

DeepSpeed-FastGen from Microsoft combines DeepSpeed-Inference’s kernels with a continuous batching engine, and it’s notable for Dynamic SplitFuse, an adaptive chunked-prefill policy covered in Chapter 18.

LMDeploy from InternLM has its own TurboMind runtime, strong quantisation support, and both NVIDIA and AMD backends.

The convergence is the useful lesson. Learning the concepts transfers between all of them, learning one engine’s implementation mostly doesn’t, which is why this book teaches the former and uses the latter as illustration.

What’s actually new in 2026

Four things are moving, and they’re worth naming so you can place this book in time.

Sparse attention at long context has taken million-token serving from possible to economical, by attending to a selected subset of tokens per query instead of the entire history. DeepSeek Sparse Attention and Native Sparse Attention are the reference points, and Chapter 14 covers them.

Four-bit numerics have arrived properly for weights, with NVFP4 and MXFP4 plus quantisation-aware distillation to recover accuracy, and more tentatively for the KV cache and the attention score path, which are further behind and further behind for different reasons (Chapters 11 and 31).

Getting the host out of the loop shows up as persistent megakernels, GPU-driven collectives, and CPU-free serving paths, all attacking the same overhead from different angles. Chapters 25 and 28.

Disaggregation has become the default topology at cluster scale, with KV cache transfer standardised enough that engines interoperate through it. Chapter 30.

Key Concept

The ecosystem has converged on paged KV, continuous batching, FlashAttention-style tiling, GQA, prefix caching, and speculative decoding. What separates the engines is maturity, hardware specialisation, and what they choose to optimise, not fundamental approach. Learn the concepts, then pick which engine’s answer to follow, or improve on, for each component.

Exercises

  1. Pick two engines and, from their documentation, write down what each does at the moment a request arrives and no KV blocks are free. Which behaviours are policy and which are mechanism?

  2. Upstream FlashInfer is CUDA-only. List three concrete engineering consequences for a serving engine that wants to support both NVIDIA and AMD, and describe how you’d structure the attention backend to absorb them.

  3. Build: run the same model and prompt set through two engines at identical batch size and precision. Report tokens/second, TTFT, and P99 inter-token latency, then explain any difference larger than 10% by pointing at a specific mechanism.
