MoE Memory Bandwidth & Batch Amortization

Why shared experts amortize immediately as 1/B from Batch 1, while routed experts only amortize once the active expert pool saturates.

1. The Erratum in Chapter 24 (Page 116)

In From Tin to Tokens: Building an LLM Inference Stack from Scratch in Rust (v1.0) [1], Chapter 24 examines the memory bandwidth bottlenecks of Mixture-of-Experts (MoE) decode. On page 116, the section on Quantised experts makes an assertion regarding shared experts that inverts the physical reality of GPU memory access:

Original (Inverted) Page 116

"...And watch the shared expert, which every token reads regardless of routing, so its bandwidth cost doesn’t amortise with batch the way routed experts do."

The error: Conflates sparsity (which shared experts lack) with batch amortization (which shared experts benefit from completely and immediately).

Corrected Architectural Truth

"...And watch the shared expert, which every token reads regardless of routing: like any dense weight its per-token bandwidth falls as 1/B from batch 1 (43 MB/token at B=1 → 0.67 MB/token at B=64 in DeepSeek-V3), while routed expert traffic per token only falls once the active expert set saturates — sparsity offers no saving on the shared expert, but batching does."

2. The Mathematical Proof: Dense GEMM vs. Sparse Routing

The shared expert architecture was originally pioneered by DeepSeekMoE [2] and scaled up in DeepSeek-V2 [3] and DeepSeek-V3 [4]. The underlying mathematics governs why the shared expert behaves identically to standard dense layers under batched inference.

Case A: The Shared Expert (Dense Amortization)

Let $W_{\text{shared}}$ denote the parameter weights of the shared expert FFN. Because every token $t \in \{1, \dots, B\}$ in the batch must be evaluated by the shared expert, the computation across the batch is expressed as a single standard dense General Matrix Multiply ($\text{GEMM}$):

Y_{\text{shared}} = X \cdot W_{\text{shared}} \quad \text{where } X \in \mathbb{R}^{B \times d_{\text{model}}}

Execution characteristics:

  • The weights $W_{\text{shared}}$ reside in High Bandwidth Memory (HBM/VRAM).
  • For all $B$ tokens, the GPU loads the weight tensor $W_{\text{shared}}$ exactly once per batch forward pass into registers/LDS.
\text{Total Memory Traffic}_{\text{shared}}(B) = W_{\text{shared}} \quad \text{[Constant with respect to } B\text{]}
\text{Per-Token Traffic}_{\text{shared}}(B) = \frac{W_{\text{shared}}}{B} \propto \frac{1}{B} \quad \mathbf{\implies \text{Strict } 1/B \text{ falloff starting immediately at } B=1}

Case B: Routed Experts (Dynamic Expansion to Saturation)

In contrast, routed experts employ top-$K_r$ gating out of $N_r$ available experts [5], [6]. The total number of unique experts loaded into VRAM across a batch of $B$ independent tokens is the union of activated experts, $U(B)$:

\mathbb{E}[U(B)] = N_r \cdot \left[1 - \left(1 - \frac{K_r}{N_r}\right)^B\right]

This formulation dictates two distinct operational regimes:

  1. Low-to-Medium Batch ($B \cdot K_r \ll N_r$): Because routing is distributed, tokens select mostly disjoint subsets of experts. Each additional token introduces $K_r$ new expert weights that must be fetched across the memory bus:
    \mathbb{E}[U(B)] \approx B \cdot K_r \implies \text{Per-Token Traffic} \approx \frac{(B \cdot K_r) \cdot W_{\text{expert}}}{B} = K_r \cdot W_{\text{expert}} \quad \mathbf{\text{[FLAT! Zero amortization]}}
    This lack of amortization at low batch is widely documented in systems literature as the "expert thrashing" or memory wall effect [7], [8].
  2. High Batch (Saturation, $B \cdot K_r \gg N_r$): Only after the active expert pool saturates ($\mathbb{E}[U(B)] \to N_r$) does total weight bandwidth hit its ceiling ($N_r \cdot W_{\text{expert}}$). From this point onward, per-token bandwidth finally begins decaying as $O(1/B)$ [9], [10].

4. Case Study: DeepSeek-V3 in FP8

Using the official architecture specifications from the DeepSeek-V3 Technical Report [4]:

DeepSeek-V3 Layer Specifications

  • Hidden Dimension ($d_{\text{model}}$): 7168
  • MoE Intermediate Size ($d_{\text{expert}}$): 2048
  • Architecture: 1 shared expert + 256 routed experts (top-8 active)
  • Parameters per Expert: 3 projections ($\text{gate}, \text{up}, \text{down}$) $= 3 \times 7168 \times 2048 = 44,040,192\text{ parameters}$
  • Size in FP8 (1 byte/param): $\approx 44.04\text{ MB}$ (decimal) or $\approx 42.0\text{ MiB}$ (binary) $\approx \mathbf{43\text{ MB}}$.

Evaluating the empirical bandwidth from Batch 1 to Batch 64:

  • At Batch 1:
    • Shared expert reads 1 expert $= 43\text{ MB/token}$.
    • Routed experts read 8 experts $= 8 \times 43 = 344\text{ MB/token}$.
  • At Batch 64:
    • Shared expert weights are loaded once across all 64 tokens: $43\text{ MB} / 64 = \mathbf{0.67\text{ MB/token}}$. (A 64× bandwidth reduction!)
    • Across 64 tokens selecting 8 experts each, the expected unique active routed experts is: $$\mathbb{E}[U(64)] = 256 \times \left(1 - (1 - 8/256)^{64}\right) \approx 222\text{ active experts}$$ Total routed weight read $= 222 \times 43\text{ MB} \approx 9,546\text{ MB}$.
      Per-token traffic $= 9,546\text{ MB} / 64 \approx \mathbf{149.5\text{ MB/token}}$. (Only a 2.3× reduction!)

Theoretical and empirical studies on DeepSeekMoE convergence [11] affirm that the shared expert captures fundamental universal representations across tokens, making Data Parallel (DP) replication across GPU ranks optimal without inter-GPU all-to-all communication overhead [4], [10].

5. The Collateral Error in Chapter 24, Exercise 2

At the conclusion of Chapter 24 (page 116) [1], Exercise 2 asks:

"2. DeepSeek-V3 has a shared expert plus top-8 of 256 routed. Compute the per-token weight traffic in FP8 and identify which component fails to amortise with batch."

Because of the author's inverted premise, the exercise expected the answer to be "the shared expert". But as mathematically proven above, the correct answer is the routed experts: they are the component that fails to amortize across low and medium batch sizes due to expert set expansion!
