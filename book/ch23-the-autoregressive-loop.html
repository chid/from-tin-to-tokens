Part V: Model Execution

The Autoregressive Loop

The full decode loop

1. Embed the input token(s) → h

2. For each layer 1..N:

  • a. h = decode_layer(h) (Chapter 22)

  • b. K, V for this token are appended to the cache

3. Final RMSNorm

4. LM head projection → logits

5. Sample → next token (on device)

6. Append the token; check stop conditions

7. Repeat

Each iteration produces one token per sequence, and the loop ends on EOS, maximum length, a stop string, or cancellation.

The LM head isn’t free

Step 4 projects from hidden size to vocabulary, which for Qwen3 is 4,096 × 151,936, about 622M parameters and 1.2 GB in FP16, and it gets read once per decode step. On a dense model that’s larger than several transformer layers. On this MoE it isn’t, because a layer carries 128 experts, but it is still around 1.2 GB that has to move for every token no matter how few experts fired.

Two consequences. At small batch the LM head can be 1 to 2% of the per-token time on its own, and at small hidden sizes with large vocabularies it can be much more. And under tensor parallelism the LM head is typically column-parallel across ranks, each producing a slice of the vocabulary, which means top-k and top-p sampling needs either a gather of the full logits or a distributed top-k. Distributed top-k, where each rank finds its local top-k followed by a small all-gather and a merge, moves kilobytes instead of hundreds of kilobytes and is the right implementation.

If the model ties input and output embeddings, through tie_word_embeddings , the LM head shares storage with the embedding table, which is worth knowing because loading it twice wastes 1.2 GB. Qwen3-235B doesn’t tie, many smaller models do.

Per-layer KV cache growth

Each decode step appends one K and one V per KV head per layer, and with paging that means writing into the current block if it has room and allocating a new one plus extending the block table if it doesn’t.

The append is a tiny kernel writing a few kilobytes, and it’s a surprisingly common source of overhead because a naive implementation dispatches it separately per layer per head. Fuse it into the RoPE kernel’s epilogue, since the data is already in registers at that point.

Growth is append-only, and existing entries are never modified during decode, which is what makes prefix sharing safe. A block referenced by two sequences can only be extended by allocating new blocks, never by mutation.

Sampling belongs on the device

Chapter 20 covered this and it’s repeated here because it’s a loop-structure decision. Run the sampler as GPU kernels and transfer only sampled token IDs, because shipping a batch × 151,936 logits tensor to the host every step both costs more than the sampling and serialises the loop.

The host still needs the sampled IDs for stop-condition checking and detokenisation, so there’s one small device-to-host transfer per step, and that transfer sits on the critical path. Hiding it, by overlapping with the start of the next step’s first layers or by checking stop conditions on device, is a real optimisation at high token rates.

The per-token cost model

T_token ≈ T_embed + N_layers × T_layer + T_lm_head + T_sample + T_host

with T_layer decomposing into attention, which reads the KV cache and is linear in context length and dominant when context is long, FFN or MoE, which reads weights and is constant in context length and dominant when context is short, elementwise work that’s individually cheap and numerous, communication of two all-reduces per layer under TP, and host overhead, the per-dispatch cost multiplied by dispatches per layer.

The model tells you where to look.

REGIME DOMINANT TERM FIX
Short context, small batch Weight bandwidth plus host overhead Quantise weights, fuse dispatches, graphs
Medium context Weights and KV comparable Quantise both
Long context (>32K) KV bandwidth Quantise KV, sparse attention, better kernels
Large batch Compute and communication Better GEMM shapes, overlap comms

A concrete anchor from mainarch’s unfused implementation. An assembled Qwen3-architecture layer measured 4.6 ms per layer with roughly 350 host round-trips , so about 13 µs per dispatch-and-wait cycle, and 94 such layers would be 430 ms per token with nearly all of it host overhead.

That number is not what a decode layer costs. It’s what an unfused, one-dispatch-per-head implementation costs, and the next two chapters are about removing it. Quoting it as the cost of a decode layer would be exactly the kind of context-free benchmarking Chapter 37 warns about.

Stop conditions

There’s usually more than one EOS token , since chat models often have a distinct end-of-turn token that also has to stop generation. Maximum length gets checked against both generated tokens and total context. Stop strings are a text-level condition on a token-level loop, so the stop string can straddle token boundaries and the output has to be truncated at the string rather than the token, which is why the detokeniser’s hold-back buffer from Chapter 20 is part of the stop-condition machinery rather than a cosmetic detail. And cancellation , when the client disconnects, wants prompt detection so KV blocks and GPU time get freed, because a system that only notices at the end of generation wastes both.

Key Concept

The autoregressive loop is the outermost structure and its per-token cost is a sum you can write down, layers times attention plus FFN plus elementwise plus communication plus host overhead, plus a surprisingly expensive LM head. Which term dominates depends on context length, batch size, and how fused your dispatch path is. Sample on device, transfer only token IDs, and treat stop strings as a textlevel condition the token-level loop has to be careful with.

Exercises

  1. For Qwen3-235B in FP8 with TP=8, estimate each term of the cost model at batch 1 and context 4K, then again at context 512K. Which term dominates in each case, and by how much?

  2. Compute the cost of the LM head as a fraction of a decode step at batch 1 and batch 64. Why does the fraction fall with batch size?

  3. Design a distributed top-k for a vocabulary-parallel LM head across 8 ranks. How many bytes cross the fabric, against gathering full logits?

  4. Build: instrument your decode loop to report per-phase timing for embedding, per-layer, LM head, sampling, and host. Run at two context lengths and confirm the predicted shift in dominant term.
