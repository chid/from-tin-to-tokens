Part III: Attention and the KV Cache

KV Cache Memory Management

PagedAttention as virtual memory

The real innovation in PagedAttention isn’t the block table, it’s treating the KV cache as a virtual memory system, and the analogy is close enough to be structural rather than decorative.

OS VIRTUAL MEMORY PAGEDATTENTION KV CACHE
Process Request (sequence)
Virtual address space Logical KV cache (token positions)
Physical page Physical KV block in VRAM
Page table Block table
Page allocator Block allocator
Copy-on-write Beam and fork divergence
Shared page Shared prefix blocks
Page eviction KV eviction under memory pressure
Swap to disk Offload to host RAM or NVMe

The algorithms, data structures, and trade-offs all transfer directly, which is why the field converged on this design so fast. It had been debugged over three decades in a different domain.

The analogy has one important limit. An OS can page a process out and back in transparently because the process’s state is the pages, whereas a sequence’s KV cache can also be regenerated from the prompt by recomputation, which has no OS analogue and gives the scheduler a choice, evict and recompute against swap out and restore, that a kernel VM subsystem never has.

Block allocation

On admission the scheduler decides there’s capacity, the allocator assigns physical blocks for the prompt’s KV, a block table gets created, and as tokens are generated blocks are appended on demand. On completion the blocks return to the free pool and the table is destroyed.

Pool size is total VRAM minus weights, activations, and workspace, and getting that number right is one of the highest-leverage configuration decisions in a deployment, because it directly sets maximum concurrency. Engines typically profile a forward pass at startup to measure peak activation memory, then hand the remainder to the KV pool.

Copy-on-write for forking

Beam search, parallel sampling with n > 1 , and speculative tree verification all create sequences that share a prefix and then diverge, and copy-on-write handles that exactly as fork() does. Divergent candidates share the prefix’s physical blocks under a reference count, new tokens go into newly

allocated blocks, and if a candidate has to modify a shared partially filled block that block gets copied first.

Only divergent blocks get duplicated, which is the difference between beam search being affordable and not.

Prefix caching

Many requests share a prefix, a system prompt or few-shot examples or a conversation history or a repeated document, and prefix caching keeps the computed KV blocks so the shared part gets computed once.

vLLM hashes the token IDs of each full block, chained with the previous block’s hash so that identical content at different positions doesn’t collide, then looks up incoming blocks and reuses hits. SGLang’s RadixAttention maintains a radix tree keyed by token sequences with physical blocks at the nodes, traverses to find the longest matching prefix, shares the matched blocks, and allocates for the remainder.

Chapter 17 covers the trade-offs. The management-level point is that both need reference counting, and both make eviction policy interesting, because a block can be free from its original sequence’s perspective while being retained as a cached prefix another request might want.

Eviction policies

When memory fills and new work needs blocks, you can run LRU over the free-but-cached blocks, which is simple, effective, and the default. You can be tree-aware and evict leaves before internal nodes, since an internal node is a prefix of everything beneath it and therefore likelier to be reused. Reference counting keeps blocks belonging to live sequences unevictable so only the cached-and-unreferenced set is in play. And you can weight by priority, protecting blocks belonging to important tenants or to prefixes with observed high hit rates.

The tension is between memory utilisation, which wants aggressive eviction so you can admit more requests, and cache hit rate, which wants the opposite. The right answer depends on the workload, and it’s worth instrumenting rather than guessing, because the ratio of prefix-cache hits to recomputed prefill tokens is one of the most informative numbers a serving system can emit.

Preemption, recompute or swap

When a running sequence has to give up its blocks, you either swap , copying its KV to host memory and restoring later at the cost of PCIe bandwidth twice plus the memory to hold it, or recompute , freeing the blocks and re-prefilling from the prompt at the cost of prefill compute proportional to the prompt length.

Writing down the comparison makes the choice obvious in either direction. For a prompt of L tokens, recompute costs roughly L divided by prefill throughput, and swap costs roughly the KV bytes for L divided by PCIe bandwidth, each way. For short prompts on fast GPUs recompute usually wins, for long prompts it doesn’t, and the crossover moves with every hardware generation, which is why engines implement both and choose per request.

Memory fragmentation

External fragmentation essentially disappears with fixed-size blocks, since any free block satisfies any request and logical contiguity comes from the table rather than from physical layout. Internal fragmentation is the partially filled last block, at most 15 wasted slots per sequence at block size 16, negligible for long sequences and material for a workload made of very short ones.

The subtler pressure is capacity planning under variance, because the allocator has to handle sequences whose final length is unknown at admission. Admit on the assumption that every sequence runs to max_tokens and you waste most of the pool, admit optimistically and you’ll sometimes preempt. Production schedulers admit optimistically, watch the free-block watermark, and preempt when it drops below a threshold.

Beyond one GPU’s memory

Two extensions matter at scale and both get chapters of their own. Offloading cold KV blocks to host RAM or NVMe adds a slower tier to the hierarchy, which is useful when prefix caches exceed VRAM. And disaggregating the KV cache into a separate service that prefill and decode nodes both address, which is Chapter 30, turns the block allocator into a distributed system with everything that implies.

Key Concept

PagedAttention’s real innovation is the memory manager, treating KV cache as paged virtual memory with block allocation, copy-on-write for forks, shared blocks for prefixes, reference counting, and eviction under pressure. Cutting KV memory waste to near zero is what delivered vLLM’s measured 2 to 4× end-to-end throughput gain. Unlike an OS, the scheduler can also regenerate evicted state by recomputation, and choosing between recompute and swap is a cost comparison rather than a policy preference.

Exercises

  1. A 48 GB pool with block size 16 serving a 94-layer model with 4 KV heads of dimension 128 in FP8. How many tokens fit? How many concurrent 8K-context sequences? How does the answer change at block size 128?

  2. Derive the crossover prompt length at which swapping beats recomputation, given a prefill rate of 20,000 tokens/s and a PCIe 5.0 ×16 link. State your assumptions.

  3. Design an eviction policy for a mixed workload where 70% of requests share one of five system prompts and 30% are unique long documents. Justify it against LRU.

  4. Build: implement a block allocator with reference counting and copy-on-write. Write a test that forks a sequence, verifies blocks are shared, diverges it, and verifies only the divergent blocks were copied.
