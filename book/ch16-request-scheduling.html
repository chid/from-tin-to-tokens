Part IV: The Serving Engine

Request Scheduling

What the scheduler is actually optimising

Take the obvious objective, maximise tokens per second, and you get a scheduler that admits everything, runs enormous batches, and misses every latency target while reporting excellent numbers. The metric that matches the business is goodput , tokens per second delivered by requests that met their service-level objectives.

The SLOs are usually TTFT , time from arrival to first output token, dominated by queueing and prefill, and TPOT or inter-token latency, the streaming rate the user perceives. End-to-end latency for a fixed output length is TTFT plus (tokens − 1) × TPOT.

A request that finishes but blew its TTFT target consumed GPU time and produced nothing of value, so measuring goodput rather than raw throughput changes scheduling decisions materially. It’s the first thing to instrument.

Admission control

When a request arrives the scheduler admits it, queues it, or rejects it.

Memory feasibility is the hard constraint, since admitting a request needs blocks for its prompt plus headroom for the tokens it will generate. Output length is unknown, so engines admit optimistically and lean on preemption, but purely optimistic admission thrashes, and the practical policy is a watermark . Admit while free blocks exceed a threshold, stop below it. That single knob is the most effective defence against preemption storms.

Queueing delay is the soft constraint, because admitting into an already large batch raises everyone’s TPOT, and a scheduler with a latency objective sometimes has to leave capacity unused.

Load shedding is the honest response to sustained overload. Return 429 or 503 quickly rather than accepting work that will miss its SLO, because a queue that grows without bound turns a throughput problem into a latency catastrophe and every request in it fails eventually anyway.

Preemption

When memory runs out something has to give, and Chapter 13 covered the cost comparison between swapping and recomputing. Two policy points sit on top of it.

Prefer to preempt the most recently admitted request rather than the longest-running one, since the newest has generated the least work to throw away and preempting a nearly finished request wastes the most.

And preemption should be rare by construction. If your preemption rate runs above a few percent of admissions, the watermark is wrong rather than the preemption policy.

Priority and fairness

Multi-tenant systems carry heterogeneous requirements, interactive chat wanting low latency, batch evaluation wanting throughput, real-time voice carrying hard deadlines.

A strict priority queue starves low-priority work indefinitely and the failure looks like a hang rather than slowness, which makes it hard to diagnose from the outside. Fair schedulers, deficit round-robin or weighted fair queuing, guarantee every class a share. Most production engines settle on priority classes with FIFO inside each class plus an ageing term so a waiting request’s effective priority rises over time, which is enough for almost everything, and simpler is genuinely better here because this code runs every iteration.

Queue discipline

FIFO is simple and fair and ignores prompt length and priority. Shortest-job-first minimises mean latency and starves long prompts, and since output length is unknown, “shortest job” is a guess anyway. Deadline-based scheduling suits real-time workloads. And prefix-aware ordering, preferring requests whose prefix is already cached because they need less prefill, is nearly free throughput on agentic workloads, though it can starve cold-prefix requests without an ageing term.

The scheduler is on the critical path

It runs every iteration, every few milliseconds. Take 2 ms to decide when the step takes 10 ms and you’ve lost 20% of the machine, so there are two structural responses.

Run it asynchronously. vLLM V1 decouples scheduling from execution so the scheduler prepares step t+1 while the GPU runs step t , hiding scheduling latency entirely as long as it stays below the step time.

Keep per-step work incremental. Rebuilding batch metadata from scratch each iteration is O(batch × blocks), while maintaining it as a persistent structure and applying diffs is O(changes). That’s exactly what vLLM’s persistent batch does, and it’s the difference between a Python scheduler being viable and not. The principle applies in any language, since the scheduler’s cost has to be proportional to what changed rather than to the size of the state.

Cost models

To pack a batch well the scheduler has to predict how long a candidate batch will take, and a serviceable model is

t_step ≈ t_weights + Σ_i t_attn(len_i) + t_prefill(tokens)

where t_weights is roughly constant, since weights get read once per step regardless of batch, t_attn is linear in each sequence’s context length, and t_prefill is roughly linear in prefill tokens at fixed chunk size. Fitting those three coefficients from live measurements gives a predictor good enough to hold iteration time inside a target band, which is what makes TPOT stable.

Two things break that model and both are increasingly common. Sparse attention makes t_attn depend on the selected budget rather than context length, and MoE makes t_weights depend on how

many distinct experts the batch activates, which is itself batch-dependent. A scheduler using the naive model on either will mis-predict systematically.

Key Concept

The scheduler maximises goodput, tokens delivered within SLO, rather than raw throughput, under a memory budget set by the KV cache. Its decisions are admission, watermark-based and optimistic without being reckless, preemption, rare by construction and chosen by cost, and priority, classes with ageing rather than strict ordering. It runs on the critical path so it has to be asynchronous and incremental, and it needs a cost model good enough to hold iteration time in a band.

Exercises

  1. Define goodput precisely for a workload with a 500 ms TTFT SLO and a 50 ms TPOT SLO, then construct a scenario where raising batch size raises throughput and lowers goodput.

  2. Derive the free-block watermark that keeps preemption below 1% for a workload where output lengths are exponentially distributed with mean 200 and the pool holds 100,000 tokens. State your assumptions.

  3. Prefix-aware queueing improves throughput and can starve cold-prefix requests. Design an ageing scheme that bounds the starvation and show the bound.

  4. Build: instrument your scheduler simulator to report goodput at several SLO pairs and find the batch cap that maximises it. Compare with the cap that maximises raw throughput.
